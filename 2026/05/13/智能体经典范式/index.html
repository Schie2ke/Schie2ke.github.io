agent经典范式

发表于2026-05-13|更新于2026-05-21|AI agent

本文将介绍以下三种agent范式:

  1. ReAct(Reasoning and Acting)： 一种将“思考”和“行动”紧密结合的范式，让智能体边想边做，动态调整。

2.Plan-and-Solve： 智能体首先生成一个完整的行动计划，然后严格执行。

3.Reflection： 一种赋予智能体“反思”能力的范式，通过自我批判和修正来优化结果。

ReAct

ReAct的核心思想是模仿人类解决问题的方式，将推理 (Reasoning) 与行动 (Acting) 显式地结合起来，形成一个“思考-行动-观察”的循环。

ReAct通过一种特殊的提示工程来引导模型，使模型每一步的输出都遵循固定的轨迹。

  • 思考(Thought)：智能体分析任务，分解任务，制定下一步计划，或反思上一步的成果。

  • 行动(Action)：智能体采取的具体行动，通常是调用一个工具。

  • 观察(Observation)：执行Action后从外部工具返回的结果，例如搜索结果的摘要或API的返回值。

智能体将不断重复这个 Thought -> Action -> Observation 的循环，将新的观察结果追加到历史记录中，形成一个不断增长的上下文，直到它在Thought中认为已经找到了最终答案，然后输出结果。这个过程形成了一个强大的协同效应：推理使得行动更具目的性，而行动则为推理提供了事实依据。

ReAct机制适用于以下场景:

  1. 多步骤信息查询任务
    例如搜索资料、查数据库、读文档后回答问题。
    ReAct 可以先判断要查什么，再调用工具，再根据结果继续追问或总结。

  2. 需要外部工具的任务
    例如调用搜索引擎、计算器、代码解释器、API、数据库、浏览器等。
    它适合把“思考”和“工具调用”交替进行。

  3. 复杂问答和事实核查
    当答案不能只靠模型记忆，需要检索、验证、对比多个来源时，ReAct 很有用。

  4. 代码调试与程序分析
    例如：阅读代码、运行测试、观察报错、修改代码、再次验证。
    这是非常典型的 ReAct 流程。

  5. 任务规划与执行型 Agent
    例如自动订票、整理文件、生成报告、操作网页、管理待办事项。
    ReAct 能让 Agent 根据执行结果动态调整计划。

  6. 环境交互任务
    例如网页导航、游戏 Agent、机器人控制、模拟环境中的决策任务。
    这类任务需要观察环境状态，再决定下一步动作。

Plan-and-Solve

Plan-and-Solve的核心动机是解决思维链在处理复杂问题，多步骤时容易“偏离轨道”的问题。

与 ReAct 将思考和行动融合在每一步不同，Plan-and-Solve 将整个流程解耦为两个核心阶段，如下图所示：

  • 规划阶段 (Planning Phase)： 首先，智能体会接收用户的完整问题。它的第一个任务不是直接去解决问题或调用工具，而是将问题分解，并制定出一个清晰、分步骤的行动计划。这个计划本身就是一次大语言模型的调用产物。

  • 执行阶段 (Solving Phase)： 在获得完整的计划后，智能体进入执行阶段。它会严格按照计划中的步骤，逐一执行。每一步的执行都可能是一次独立的 LLM 调用，或者是对上一步结果的加工处理，直到计划中的所有步骤都完成，最终得出答案。

Plan-and-Solve 尤其适用于那些结构性强、可以被清晰分解的复杂任务，例如：

  1. 复杂推理任务
    例如数学题、逻辑题、多条件判断题。
    先制定解题步骤，再逐步求解，可以减少遗漏。

  2. 多步骤执行任务
    例如“帮我写一份市场分析报告”“设计一个课程大纲”“制定旅行计划”。
    这类任务需要先拆成若干子任务，再分别完成。

  3. 长文本生成任务
    例如论文、方案、商业计划书、技术文档。
    先规划结构，再填充内容，结果通常更完整。

  4. 项目规划类任务
    例如产品路线图、研发计划、活动策划、学习计划。
    这类任务天然需要阶段、里程碑、资源和风险安排。

  5. 代码开发与系统设计
    例如设计模块、拆分功能、规划接口、实现复杂功能。
    Plan-and-Solve 可以先确定架构和步骤，再进入实现。

  6. 需要避免遗漏的任务
    例如合规审查、需求分析、测试用例设计、风险评估。
    先列计划有助于覆盖关键维度。

Reflection

Reflection机制

Reflection的核心流程如下:

  1. 执行 (Execution)：首先，智能体使用我们熟悉的方法（如 ReAct 或 Plan-and-Solve）尝试完成任务，生成一个初步的解决方案或行动轨迹。这可以看作是“初稿”。

  2. 反思 (Reflection)：接着，智能体进入反思阶段。它会调用一个独立的、或者带有特殊提示词的大语言模型实例，来扮演一个“评审员”的角色。这个“评审员”会审视第一步生成的“初稿”，并从多个维度进行评估，例如：

  • 事实性错误：是否存在与常识或已知事实相悖的内容？
  • 逻辑漏洞：推理过程是否存在不连贯或矛盾之处？
  • 效率问题：是否有更直接、更简洁的路径来完成任务？
  • 遗漏信息：是否忽略了问题的某些关键约束或方面？ 根据评估，它会生成一段结构化的反馈 (Feedback)，指出具体的问题所在和改进建议。
  1. 优化 (Refinement)：最后，智能体将“初稿”和“反馈”作为新的上下文，再次调用大语言模型，要求它根据反馈内容对初稿进行修正，生成一个更完善的“修订稿”。

与前两种范式相比，Reflection 的价值在于：

  • 它为智能体提供了一个内部纠错回路，使其不再完全依赖于外部工具的反馈（ReAct 的 Observation），从而能够修正更高层次的逻辑和策略错误。

  • 它将一次性的任务执行，转变为一个持续优化的过程，显著提升了复杂任务的最终成功率和答案质量。

  • 它为智能体构建了一个临时的“短期记忆”。整个“执行-反思-优化”的轨迹形成了一个宝贵的经验记录，智能体不仅知道最终答案，还记得自己是如何从有缺陷的初稿迭代到最终版本的。更进一步，这个记忆系统还可以是多模态的，允许智能体反思和修正文本以外的输出（如代码、图像等），为构建更强大的多模态智能体奠定了基础。

Reflection成本和收益分析

主要成本:

  1. 模型调用开销增加:这是最直接的成本。每进行一轮迭代，至少需要额外调用两次大语言模型（一次用于反思，一次用于优化）。如果迭代多轮，API 调用成本和计算资源消耗将成倍增加。

  2. 任务延迟显著提高:Reflection 是一个串行过程，每一轮的优化都必须等待上一轮的反思完成。这使得任务的总耗时显著延长，不适合对实时性要求高的场景。

  3. 提示工程复杂度上升:如我们的案例所示，Reflection 的成功在很大程度上依赖于高质量、有针对性的提示词。为“执行”、“反思”、“优化”等不同阶段设计和调试有效的提示词，需要投入更多的开发精力。

核心收益

  1. 提高方案质量:最大的收益在于，它能将一个“合格”的初始方案，迭代优化成一个“优秀”的最终方案。这种从功能正确到性能高效、从逻辑粗糙到逻辑严谨的提升，在很多关键任务中是至关重要的。

  2. 鲁棒性与可靠性增强:通过内部的自我纠错循环，智能体能够发现并修复初始方案中可能存在的逻辑漏洞、事实性错误或边界情况处理不当等问题，从而大大提高了最终结果的可靠性。
