主流智能体框架（一）

发表于2026-05-17|更新于2026-05-18|AI agent

Microsoft Agent Framework

Microsoft Agent Framework，简称 MAF，不是凭空出现的。它主要继承了微软此前两条技术路线：

  1. AutoGen：偏研究和多 Agent 协作，核心是“多个 Agent 通过消息对话完成复杂任务”。
  2. Semantic Kernel：偏企业应用和生产工程，核心是“把 LLM、插件、函数、数据源、观测、安全治理接入应用”。

MAF 可以理解为这两条路线的合流：把 AutoGen 的多 Agent 编排能力，和 Semantic Kernel 的企业级工具、状态、类型、安全、观测能力整合到一个统一框架里。

AutoGen

AutoGen 是微软研究院推出的多 Agent 框架。它的核心思想很直接：复杂任务不一定由一个 Agent 独自完成，可以由多个角色不同的 Agent 通过对话协作完成。

比如一个“写研究报告”的任务，可以拆成：

  • Research Agent：负责搜索和收集资料
  • Analyst Agent：负责分析和归纳
  • Writer Agent：负责写作
  • Reviewer Agent：负责检查事实和格式
  • User Proxy Agent：代表人类参与确认或提供额外信息

这和传统程序不同。传统程序是你提前写好流程：

step1 -> step2 -> step3 -> output

AutoGen 更像一个“多人会议”：

用户提出目标
研究员 Agent 发言
分析师 Agent 接话
写作者 Agent 起草
审阅者 Agent 提修改意见
必要时请求人类确认
最终形成答案

AutoGen 的底层原理：消息驱动的多 Agent 系统

AutoGen 的关键不是“调用很多模型”，而是它把 Agent 抽象成可以收发消息的计算单元。

一个 Agent 通常包含三类能力：

  1. 接收消息：来自用户、其他 Agent、工具结果或系统事件。
  2. 处理消息：调用 LLM、执行工具、套用规则、请求人类输入。
  3. 发送消息：把结果发给另一个 Agent 或发回给用户。

底层执行逻辑可以简化成：

Message -> Agent receives -> Agent thinks/acts -> New Message -> Next Agent

AutoGen v0.4 之后更强调 actor model。Actor model 是一种并发编程模型，每个 actor 都是独立的执行单元，靠消息通信，不直接共享内部状态。用在 Agent 系统里，就是：

  • 每个 Agent 是一个 actor
  • Agent 之间不直接调用彼此内部函数
  • 它们通过消息交换协作
  • Runtime 负责消息分发、事件调度、并发执行

这带来的好处是：Agent 可以异步运行，可以分布在不同进程甚至不同语言环境里，也更适合复杂多 Agent 系统。

AutoGen 的优势和局限

AutoGen 的优势是灵活，特别适合研究和探索复杂 Agent 模式，比如：

  • Group Chat：多个 Agent 群聊
  • Debate：多个 Agent 辩论
  • Reflection：一个 Agent 输出，另一个 Agent 反思修正
  • Planner / Executor：一个 Agent 规划，另一个 Agent 执行
  • Human-in-the-loop：人类中途介入

但 AutoGen 早期更偏实验。真正进入生产环境时，开发者还会遇到很多工程问题：

  • 状态如何持久化？
  • 工具权限如何控制？
  • 失败任务如何恢复？
  • 调用链如何观测？
  • 如何接入企业身份、安全、审计、监控？
  • 如何和 Azure、Microsoft 365、企业 API 稳定集成？

这正是 Semantic Kernel 擅长的部分。

Semantic Kernel

Semantic Kernel，简称 SK，是微软较早推出的企业级 LLM 应用开发 SDK。它关注的问题不是“多个 Agent 怎么聊天”，而是：

如何把 LLM 稳定地嵌入真实应用，让它能调用函数、访问数据、使用企业服务，并且可观测、可治理。

SK 的核心对象叫 Kernel。

可以把 Kernel 理解成一个“AI 应用运行容器”。它负责管理：

  • 模型服务，比如 Azure OpenAI、OpenAI
  • 插件，也就是可被模型调用的函数集合
  • Prompt 模板
  • Memory / Vector Store
  • 日志、过滤器、中间件、安全策略
  • 依赖注入服务

官方文档对 Kernel 的解释很关键：它本质上是一个管理服务和插件的依赖注入容器。

Semantic Kernel 的底层原理：函数调用循环

SK 最重要的机制是 function calling loop，也就是函数调用循环。

假设你有一个灯光控制插件：

get_lights()
change_state(light_id, is_on)

用户说：

把所有灯切换一下状态

LLM 并不会直接控制灯。真实过程是：

  1. Kernel 把用户问题、历史消息、可用函数 schema 发给模型
  2. 模型判断：我需要先调用 get_lights()
  3. Kernel 解析模型返回的函数调用请求
  4. Kernel 在真实代码中执行 get_lights()
  5. Kernel 把工具结果返回给模型
  6. 模型继续判断：需要调用 change_state(…)
  7. Kernel 再次执行函数
  8. 模型看到最终结果，生成自然语言回复

这就是 Agent 工具调用的核心机制。

注意，这里所谓“模型会调用工具”，不是模型真的拥有权限。更准确地说：

模型只是输出一个结构化的工具调用意图，框架负责校验、执行和返回结果。

这点非常重要。Agent 的安全边界不在模型内部，而在框架和工具执行层。

Plugin、Function、Tool 的关系

在 Semantic Kernel 里，常用词是 Plugin 和 Function。

  • Plugin：一组相关函数的集合，例如 CalendarPlugin、EmailPlugin、DatabasePlugin。
  • Function：插件里的一个具体能力，例如 send_email、query_sales。
  • Tool：更通用的说法，其他框架通常把可调用函数都叫 Tool。

可以这样理解：

Plugin = 工具箱
Function = 工具箱里的某个工具
Tool = Agent 可调用能力的通用名称

SK 的优势在于，它让企业开发者可以把已有代码、REST API、OpenAPI 服务、MCP Server 封装成插件，让 LLM 通过函数调用使用它们。

Semantic Kernel 的工程价值

SK 比较强的地方是工程化：

  • 通过依赖注入管理服务
  • 通过插件封装企业 API
  • 通过 function calling 实现自动规划
  • 通过 Vector Store 做 RAG
  • 通过 Filters / Middleware 做拦截、审计、权限控制
  • 通过 Observability 做日志和追踪
  • 通过多语言 SDK 支持 .NET、Python、Java

也就是说，SK 的核心思想不是“让 Agent 更会聊天”，而是：

让 LLM 应用像正常企业软件一样被构建、测试、监控和治理。

为什么 AutoGen 和 Semantic Kernel 需要结合

AutoGen 和 Semantic Kernel 解决的是同一个大问题的不同侧面。

AutoGen 擅长：

多 Agent 协作
动态对话
复杂任务分工
研究型编排模式

Semantic Kernel 擅长：

工具接入
企业集成
函数调用
状态管理
安全治理
可观测性
生产稳定性

如果只用 AutoGen，你可能很快做出一个多 Agent Demo，但生产化时要自己补很多基础设施。

如果只用 Semantic Kernel，你可以很好地接工具和企业系统，但早期多 Agent 编排和复杂动态协作不是它最核心的表达方式。

所以微软后来把两条路线收敛成 Microsoft Agent Framework。

MAF

Microsoft Agent Framework 是微软新的统一 Agent 框架。官方定位是：用于构建、编排和部署生产级 AI Agent 与多 Agent Workflow 的开源、多语言框架，支持 Python 和 .NET。

MAF 的设计可以概括成四个核心对象：

Agent + Tool + Session + Workflow

它不是简单把 AutoGen 和 SK 名字放在一起，而是重新整理了底层抽象。

Agent 不再依赖单一 Kernel 中心

在 Semantic Kernel 里，Kernel 是中心。模型、插件、服务都挂在 Kernel 上。

而 MAF 更偏向直接的 Agent 抽象：

Chat Client -> Agent -> Run

也就是说，你先有一个模型客户端，比如 Azure OpenAI、OpenAI、Foundry、Anthropic，然后把它包装成 Agent，再给 Agent 配置 instructions、tools、session、middleware。

这让结构更清晰：

Provider 提供模型能力
Chat Client 负责和模型通信
Agent 负责组织任务执行
Tool 提供外部行动能力
Session 保存上下文
Workflow 负责编排多个执行单元

工具调用仍然是 Agent 行动的核心

MAF 里的 Tool，本质上继承了 SK 的 function calling 思想。

执行流程依然是：

用户输入
-> Agent 构造上下文
-> 模型判断是否需要工具
-> 返回结构化工具调用
-> 框架执行工具
-> 工具结果回填上下文
-> 模型继续判断或生成最终答案

区别在于 MAF 把 Tool 表达得更统一。无论工具来自：

  • 本地函数
  • OpenAPI
  • MCP Server
  • File Search
  • Web Search
  • Code Interpreter
  • 另一个 Agent

都可以被 Agent 作为能力使用。

甚至一个 Agent 可以被包装成另一个 Agent 的 Tool。这意味着可以形成层级结构：

主 Agent
-> 天气 Agent 工具
-> 财务 Agent 工具
-> 搜索 Agent 工具

Session 和 Context Provider 管理“记忆”

Agent 看起来会记住上下文，其实不是模型自己永久记住了，而是框架在每次调用时把相关上下文重新组织后发给模型。

MAF 中常见流程是：

  1. 创建 AgentSession
  2. 用户发起一轮请求
  3. Context Provider 注入相关信息
  4. History Provider 加载历史消息
  5. Agent 调用模型和工具
  6. 执行结束后更新 Session 状态
  7. 下一轮继续使用同一个 Session

这里有几个关键概念：

  • Session：当前任务或对话的状态容器。
  • History：历史消息。
  • Context Provider：负责注入额外上下文，比如用户偏好、检索结果、长期记忆。
  • Persistence：把 Session 或历史保存到内存之外，方便恢复。

所以 Agent 的“记忆”本质上是：

存储系统 + 检索逻辑 + 上下文注入

Workflow 解决可控编排

AutoGen 强调多 Agent 对话，但企业流程经常需要更确定的路径。MAF 因此提供 Workflow。

Workflow 是图结构：

Executor A -> Executor B -> Executor C

其中：

  • Executor 是执行节点，可以是函数，也可以是 Agent。
  • Edge 是连接线，决定数据从哪里流向哪里。
  • WorkflowBuilder 用来构建图。
  • Checkpoint 用来保存中间状态。
  • Event 用来观察执行过程。

如果 Agent 是“让模型动态决定下一步”，Workflow 就是“开发者明确规定流程”。

例如报销审批：

读取报销单
-> 检查发票
-> 风险评分
-> 高风险请求人工审批
-> 低风险自动通过
-> 生成结果

这个流程不应该完全交给 LLM 自由发挥。应该用 Workflow 明确控制，而在某些节点中调用 Agent 做非结构化分析。

这就是 MAF 很重要的设计哲学：

能用确定性代码解决的，不要交给 Agent；需要语言理解和开放推理的，再交给 Agent。

Superstep 让并发更可控

MAF Workflow 文档提到一种类似 Pregel / BSP 的 superstep 执行模型。

第 N 轮：
收集所有待处理消息
根据边路由到目标 Executor
并发执行这些 Executor
等待全部完成
把新消息放入下一轮

第 N+1 轮：
继续处理

这和普通异步任务不同。它在每一轮之间设置同步点。

好处是：

  • 执行顺序更确定
  • 并发行为更容易推理
  • Checkpoint 更可靠
  • 出错后更容易恢复

代价是：某些并发路径可能会互相等待。因此设计 Workflow 时，要避免把可以合并的连续小步骤拆得太碎。

MAF 如何融合 AutoGen 和 Semantic Kernel

可以用一张逻辑表理解：

来源 原有能力 在 MAF 中的体现
AutoGen 多 Agent 对话 Agent orchestration
AutoGen Actor / event-driven 思想 消息、事件、异步执行
AutoGen GroupChat、handoff、concurrent 多 Agent 编排模式
Semantic Kernel Kernel + Plugin Agent + Tool
Semantic Kernel Function calling loop Tool invocation loop
Semantic Kernel Memory / Vector Store Context Provider / History Provider
Semantic Kernel Filters / Observability Middleware / Telemetry
Semantic Kernel 企业集成 Foundry、Azure OpenAI、MCP、OpenAPI、A2A

MAF 的合并不是把两个框架简单拼接，而是把共同底层抽象统一成：

消息输入
-> Agent 或 Workflow 处理
-> 模型调用
-> 工具调用
-> 状态更新
-> 事件输出
-> 可观测和可恢复
